before changing files under these paths:

- `frontend/src/components/timeline/AGENTS.md` — timeline graph behavior

## Development Environment

Use the `intercept` Conda environment for repository commands.

```bash
conda activate intercept
```

If `conda` is not on `PATH` in a non-interactive shell, initialize it first:

```bash
eval "$(~/miniconda3/bin/conda shell.bash hook)"
conda activate intercept
```

## Repository Architecture

Intercept is a monorepo with a FastAPI backend, a React/TypeScript frontend, and
PostgreSQL persistence.

- FastAPI routers live in `backend/app/api/routes/`. Keep transport concerns in
  routers and put business logic in `backend/app/services/`.
- The primary SQLModel tables and API schemas live in
  `backend/app/models/models.py`; shared enums live in
  `backend/app/models/enums.py`.
- Frontend API contracts and service clients are generated under
  `frontend/src/types/generated/` and are committed to the repository.
- Frontend route-level components live in `frontend/src/pages/`; reusable data
  access and mutation logic generally lives in `frontend/src/hooks/`.

## Backend API Contract Changes

After a backend change alters the OpenAPI contract (for example, a request or
response schema or an endpoint), regenerate the frontend API client from the
repository root:

```bash
./scripts/generate-types.sh
```

The generator imports the FastAPI application, reads `app.openapi()`, and
replaces `frontend/src/types/generated/`. Generated field names preserve the
backend's `snake_case` spelling. Do not hand-edit generated files; review and
commit the generated diff with the backend change.

Frontend code should consume API models and clients from the generated package,
for example:

```typescript
import type { CaseRead } from "@/types/generated/models/CaseRead";
import { CasesService } from "@/types/generated/services/CasesService";
```

## Database Schema Changes

Alembic is the source of truth for application schema. From `backend/`:

```bash
alembic revision --autogenerate -m "description"
alembic upgrade head
```

Always review autogenerated migrations. PostgreSQL enum changes and some
PostgreSQL-specific objects require manual migrations; follow
`docs/database-schema-management.md` rather than assuming autogenerate is
complete.

## Validation

Run the smallest relevant checks while developing. The standard suites are:

```bash
# Backend
cd backend && pytest

# Frontend typecheck and unit/component tests
cd frontend && npx tsc --noEmit
cd frontend && npm test

# Browser end-to-end tests
cd frontend && npx playwright test
```

`./scripts/fast-ci-local.sh --skip-images` runs the repository's change-aware
backend selection plus the frontend typecheck and tests. Use `--full` when the
complete backend suite and image-build checks are warranted.

## Version Management

**All version bumps MUST use `bump-my-version`.** Never edit version strings manually.

```bash
conda activate intercept
bump-my-version bump patch   # 0.0.8 → 0.0.9
bump-my-version bump minor   # 0.0.8 → 0.1.0
bump-my-version bump major   # 0.0.8 → 1.0.0
```

### What it does

A single `bump-my-version bump <part>` command:

1. Updates version in all managed files (see `.bumpversion.toml`):
   - `VERSION`
   - `frontend/package.json`
   - `frontend/package-lock.json`
2. Creates a git commit (`release: v{new_version}`)
3. Does **not** create a git tag. The GitHub Release workflow creates `v{new_version}` after the version bump commit is merged to `main`.

### When to bump

- **After** all code changes for the release are committed on the release branch
- **Before** merging the release branch to `main`
- Bump should be the final commit on the release branch before merge
- After the merge reaches `main`, `.github/workflows/release.yml` creates the `v{new_version}` tag from `VERSION` and runs the release

### Adding new versioned files

If a new file contains the version string and should be updated on bump, add a `[[tool.bumpversion.files]]` entry to `.bumpversion.toml`. Commit the config change before running the bump.

### Important

- The working directory must be clean (no uncommitted changes) before running `bump-my-version`
- If you need to fix something after bumping but before merging to `main`, reset the bump commit (`git reset --soft HEAD~1`), make your fix, commit it, then re-run `bump-my-version bump <part>`
- Do not create or push release tags manually; release tags are owned by `.github/workflows/release.yml`
